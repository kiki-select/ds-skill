# 抽样校验方法论

**主查询跑完后，从结果里挑样本回到原始事件做反向验证。聚合 SQL 写对≠语义对。**

## 为什么必须做

聚合 SQL 写对了不代表语义对 —— 同一组 `countIf` 条件可能漏掉 NULL、双计某种 stat、把跨天事件并到一天。这类错误**不会报错**，主查询跑出来"看起来有数"但其实算错了。**抽样比对原始记录是发现这类错误的最便宜手段**。

---

## 触发场景（任一命中就抽）

- 主查询出了任何指标（成功率、消耗、时长、留存…）
- 数值看着「差不多对」但没有 ground truth
- 涉及多 stat / 多事件 union / argMax 这类容易绕错的逻辑

---

## 抽样原则

- **挑代表性样本，不是随机** —— 一个高活跃 + 一个中等 + 一个边界（如指标极值所在的维度）
- **数量少而精** —— 1~3 个 pid 足够，多了也看不过来
- **手算可复现** —— 抽出来的原始事件，用 Excel/口算就能复现主查询的聚合数

---

## 校验模板

### 模板 1：用户样本完整事件流（最常用）

先从主查询结果里挑 pid（如某模式下当天匹配最多的 1 个 pid），然后：

```sql
select `#time`, <关键字段>
  from events
  where `#event` = '<事件名>'
    and `#dt` = '<日期>'
    and pid = <挑出的 pid>
  order by `#time`
```

**人工核对**：该 pid 的指标按口径手算 = 主查询那一行。例如：
- 主查询说「pid=12345 当天匹配成功 8 次」
- 抽样回查：该 pid 当天 `match_stat=3` 的事件应该正好 8 条

### 模板 2：维度切片精确回查

按主查询的某个 group 维度精确还原，不展开样本：

```sql
select countIf(<条件 A>) as a,
        countIf(<条件 B>) as b
  from events
  where `#event` = '<事件名>'
    and `#dt` = '<日期>'
    and <主查询的 group 维度精确还原>
```

**期望**：与主查询那一行严格相等。例如：
- 主查询输出「2026-04-20 mmod=10001 总场次=N，成功=M」
- 反查 `mmod=10001` 单维度 → 数字必须完全一致

### 模板 3：极值样本（看异常上限是否真合理）

如主查询里某模式 `max_wait_sec = 3600`（1 小时），抽具体那条事件看是否数据脏：

```sql
select pid, <相关字段>
  from events
  where `#event` = '<事件名>'
    and `#dt` = '<日期>'
    and <极值发生的维度>
  order by <极值字段> desc
  limit 5
```

**判定**：
- 极值是真实业务情况 → 主查询正确
- 极值是脏数据撑起来的 → 主查询要加范围过滤后重跑

---

## 校验通过的标准

- ≥1 个用户样本：原始事件按口径手算 = 主查询数值
- ≥1 个维度切片：精确条件回查 = 主查询那一行
- 极值样本看着合理（不是脏数据撑起来的均值/最大值）

## 不通过怎么办

- **数值偏差** → 回头查 `countIf` 条件、`group by` 维度、`#dt` 过滤是否漏写
- **极值是脏数据** → 主查询加过滤（如 `wait_sec between 0 and 600`）后重跑
- **不要直接交付 "差不多" 的结果**

---

## 文件归档约定

- 校验 SQL 写到 `queries/<场景>/verify_<内容>.sql`
- 校验结果落到 `outputs/<场景>/verify_<内容>.csv`
- **跟主查询同子目录归档**，保留决策链路

---

## 交付时附摘要

回给用户的交付内容里加一两句校验摘要：

> 抽样校验：抽 pid=12345 当天 8 条 `match_stat=3` 事件，与主查询「该 pid 当日成功匹配数=8」对得上；抽 mmod=10001 维度切片 countIf=3812，与主查询该行严格相等。

让用户知道数据不是裸跑出来的，对结果有信心。
